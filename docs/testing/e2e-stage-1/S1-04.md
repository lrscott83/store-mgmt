## User Story

Como usuario que recarga la app, quiero que mi sesión se restaure al instante desde la caché local, para que un servidor caído o ausente no me expulse.

## Precondiciones

- `localStorage` contiene `AUTH_MODEL` con `authToken` y `expiresIn`.

## Rama verificada

`shared/lib/stores/auth-store.ts:100-192` — este comportamiento es **deliberado** y merece aserción propia:

| Estado de `AUTH_MODEL` / caché | Efecto |
|---|---|
| Ausente | retorna `null`, sin llamada (`:99-100`) |
| JSON inválido | borra `AUTH_MODEL`, retorna `null` (`:103-108`) |
| Parseable pero sin `authToken` o sin `expiresIn` | retorna `null` y **no borra nada** (`:110-113`) |
| `expiresIn <= Date.now()` | `logout()` — límite **inclusivo** (`:115-120`) |
| Perfil cacheado cuyo `authToken` **coincide** | hidrata sincrónicamente y **NO hace ninguna llamada** (`:124-138`) |
| Sin caché usable | hidrata *best-effort* sincrónicamente y **luego** llama `GET /v1/auth/me` (`:144-153`) |

## Flujo

1. Autenticarse.
2. Recargar la página.

## Aserciones — Playwright (UI)

- [ ] Con caché válida, la recarga produce **cero** `GET /v1/auth/me` (`auth-store.ts:133-139` — la revalidación en segundo plano de Angular fue **removida** a propósito; el comentario explica que el 401 de ese `/me` era convertido en logout por el interceptor y rompía el uso offline).
- [ ] Sin caché usable, la recarga produce exactamente un `GET /v1/auth/me` (`auth-store.ts:155`).
- [ ] Con el servidor apagado y sin caché: el usuario **permanece autenticado** con el usuario best-effort; no hay logout (`auth-store.ts:173-190`).
- [ ] Con `GET /v1/auth/me` respondiendo **401** o **404**: se cierra la sesión y se redirige a `/login` (`auth-store.ts:39-45,185-187`). 404 es el código que `GetMeQuery` usa tanto para *NotFound* como para *AccountInactive* (comentario `auth-store.ts:29-33`).
- [ ] Con `GET /v1/auth/me` respondiendo **500**: el usuario **NO** es deslogueado (`auth-store.ts:185-190`).
- [ ] `expiresIn` exactamente igual a `Date.now()` ⇒ sesión expirada (comparación `<=`, `auth-store.ts:117`).
- [ ] `logout()` borra **solo** `AUTH_MODEL`; `token` y `currentUser` quedan obsoletos a propósito, por paridad con Angular (`auth-store.ts:352-361`).
- [ ] `logout()` **no** redirige si ya se está en `/login` o en `/` (`auth-store.ts:366-369`).

## Aserciones — .NET E2E (dato)

- [x] `GET /v1/auth/me` con token válido devuelve 200 y el usuario correcto.
- [x] Token malformado → 401.
- [x] Usuario inexistente → 404; usuario inactivo → 404, y una segunda llamada → 401 (token en lista negra).

## Pendiente para otra pasada

Tres cosas quedaron fuera del alcance de S1-04 **a propósito**, cada una con su razón.
No son omisiones: son trabajo con nombre.

### P-1 — La guarda de pathname de `logout()` no es verificable en navegador

`logout()` decide si redirige con `pathname !== '/login' && pathname !== '/'`
(`auth-store.ts:367`). Ese `if` **no se puede pinear desde Playwright** en arranque en
frío: `initialize()` corre en evaluación de módulo (`auth-store.ts:390`) mientras
`registerAuthRedirect(navigate)` corre en un `useEffect` (`root.tsx:89-91`), así que
cuando la guarda se evalúa, `authRedirect` todavía es `undefined` y el `?.()` es no-op
**cualquiera sea el pathname**. Un test de arranque en frío pasaría igual con la guarda
borrada.

Hoy la cobertura discriminante vive en `auth-store.test.ts:297-315`, con un spy real —
que es vitest, no E2E. Cubrirlo en navegador exigiría un escenario donde `logout()` se
dispare **después** de que React montó (por ejemplo un logout por inactividad), no en el
arranque. Eso es un test nuevo, con su propio diseño.

### P-2 — El 404 real de `/me` para una cuenta desactivada

`isSessionRejection` (`auth-store.ts:39-45`) evalúa 401 y 404 en la **misma expresión**,
así que la reacción del cliente al 404 **ya está cubierta** por el test del 401 (T4). La
brecha es únicamente del lado del servidor: no está verificado que el backend devuelva
404 para una cuenta desactivada.

Y no se puede montar desde la UI: **ninguna pantalla llama `activate(false)`** (H-6). Hace
falta desactivar la cuenta por otra vía. Anotado como [B-6](plan-backend.md#b-6).

### P-3 — T8 es un flake latente, sin causa raíz

El test de "logout estando en `/login` no genera navegación extra" falló **tres corridas
seguidas** reportando una navegación de más, y a la cuarta pasó **sin que se arreglara
nada**. Leer el código no la explica: el redirect está guardado en `/login`, y
`guestOnlyLoader` devuelve `null` para un visitante no autenticado (`loaders.ts:42-58`).

El test quedó instrumentado para desambiguar el próximo rojo: cuenta los requests de
documento junto a las navegaciones, así que `documents: 1` con dos navegaciones significa
que el router del cliente empujó la segunda, y `documents: 2` que hubo recarga dura.
**Está instrumentado, no resuelto.**

**Nota**: `vitest` cubre la rama clave en `shared/lib/stores/__tests__/auth-store.test.ts:440` (incluye explícitamente *"does NOT call authHttpService.getMe when a valid cached session exists"*) y `auth-store.session-rejected.test.ts:68-124` (401/404 cierran; red caída y 500 no). No es E2E.
