## User Story

Como OwnerAdmin, quiero ver, editar y dar de alta/baja a los usuarios de mi tienda, para administrar el acceso de mi equipo.

## Precondiciones

- OwnerAdmin autenticado con feature `Users`.

## Flujo

1. Ir a `/management/users` — la lista se carga una sola vez al montar.
2. Editar un usuario, guardar.
3. Desactivar un usuario; luego reactivarlo.

## Aserciones — Playwright (UI)

- [ ] Al montar se emite **exactamente un** `GET /v1/users/all/true`; navegar dentro de la pantalla no la re-dispara (fetch *mount-only* — `user-list.tsx:38-41`).
- [ ] Nótese `all/true`: la ruta es **literal** con `includeInactive=true`, así que la lista **incluye usuarios inactivos** (`user-http-service.ts:24`).
- [ ] **La acción "desactivar" emite `DELETE /v1/users/{id}`, no `POST /v1/users/activate`** (`user-list.tsx:73` → `userHttpService.deleteUser`). Ver **H-6**.
- [ ] La acción "activar" emite `POST /v1/users/activate` con `{ id, isActive: true }` (`user-list.tsx:72`; `user-http-service.ts:52-57`).
- [ ] Consecuencia: **la UI nunca llama `activate` con `isActive:false`** — ese semi-endpoint queda sin ejercitar desde la pantalla (`user-list.tsx:72-73`).
- [ ] Toda acción de ciclo de vida **no hace nada** si el navegador está offline (`user-list.tsx:47`).
- [ ] Una acción exitosa **recarga la lista** (`user-list.tsx:50`).
- [ ] Una acción fallida muestra `USERS.LIFECYCLE_ERROR` — mensaje distinto al de fallo de carga, que es `USERS.ERROR` (`user-list.tsx:27,53`).
- [ ] Editar emite `PUT /v1/users/{id}` y navega a `/management/users` (`management/users/routes/user-edit.tsx:59-60`).
- [ ] Un StoreUser en `/management/users` es deslogueado y redirigido a `/login` (`user-list.tsx:12` → `adminLoader`).
- [ ] ⚠️ **No existe scoping por tienda del lado cliente.** `/management/users/edit/:id` toma el id **de la URL** y hace `getUserById(userId)` sin ninguna comprobación de pertenencia (`user-edit.tsx:21,32-47`). La protección real es del servidor y es **por tenant** (ver **H-11**): un id de otro tenant devuelve envelope 404. Un id de otra tienda del mismo tenant es legítimo para el OwnerAdmin (dueño del tenant). La consideración restante es de UI —qué lista mostrar según `SelectedStoreId`—, producto, no seguridad.
- [ ] El toggle "activo" solo se renderiza para SuperAdmin u OwnerAdmin (`user-edit.tsx:24,106`).

## Aserciones — .NET E2E (dato)

- [x] `GET /v1/users/all/true` incluye usuarios inactivos; con `false` los excluye.
- [x] SuperAdmin y OwnerAdmin-con-feature obtienen 200; StoreUser y ReSeller obtienen 403; sin token, 401.
- [x] `DELETE /v1/users/{id}` es un **soft delete** (la fila sobrevive con la bandera cambiada).
- [x] `POST /v1/users/activate` con `true` activa y con `false` desactiva.
- [x] `PUT /v1/users/{id}` con body parcial **preserva** email y teléfono; omitir `isActive` preserva el estado.
- [x] Un SuperAdmin no puede borrarse a sí mismo → 400.
- [x] ✅ **Aislamiento cross-tenant en `PUT /v1/users/{id}`: SÍ se cumple.** La frontera de seguridad es el **tenant**, no la tienda. El filtro global sobre `User` (`Infrastructure/Persistence/EntityConfigurations/UserEntityTypeConfiguration.cs:22-24`) aplica incluso al camino `FindAsync`: un usuario de otro tenant es invisible → `user is null` → envelope 404, sin escritura. Medido por `Users/UsersIsolationTests.cs:22` (`Update_owner_admin_updates_user_in_other_tenant_returns_envelope_404`). El guard del handler (`UpdateUserCommand.cs:49-50`) solo decide la forma, nunca la pertenencia.
- [x] ✅ **Un OwnerAdmin editando un usuario de otra tienda del mismo tenant es una REGLA DE NEGOCIO, no un defecto.** El OwnerAdmin es dueño del tenant —y de todas sus tiendas—; su scope de gestión de usuarios es el tenant entero (`HttpContextService.cs:45-50`: `IsSuperAdminOrOwnerAdmin`; el `TenantId` viene del claim del JWT). Confirmado por `Users/UsersIsolationTests.cs:48` (`Update_owner_admin_updates_user_in_other_store_returns_200`). No hay —ni debe haber— comparación contra `StoreId` en el handler. Ver **H-11**.

## Estado de cobertura

**E2E backend (.NET) — CUBIERTO**

YA CUBIERTO: `Users/UsersListTests.cs:25,38,50,62,74,81,101,121,134`; `Users/UsersGetByIdTests.cs:26,39,52,59,72`; `Users/UsersUpdateTests.cs:17,31,44,57,65,79,93,115,139,162,185,208,229`; `Users/UsersDeleteTests.cs:20,46,63,70,91`; `Users/UsersActivateTests.cs:20,46,72,89`.

**MEDIDO desde entonces** (`Users/UsersIsolationTests.cs`), y el resultado define la regla de negocio:

- **Cross-tenant: SÍ aísla.** `Update_owner_admin_updates_user_in_other_tenant_returns_envelope_404` — envelope `actionCode: 404`, y el usuario ajeno **no se modifica** en base. La incógnita planteada por la primera versión de esta aserción (¿aplica el filtro al camino `FindAsync`?) quedó respondida por corrida real: **sí aplica**.
- **Cross-store: es el scope del dueño.** `Update_owner_admin_updates_user_in_other_store_returns_200` — la edición se aplica. **Regla de negocio confirmada**: el OwnerAdmin es dueño del tenant y de todas sus tiendas; la frontera de aislamiento es el tenant, no la tienda (ver **H-11**). Sin scoping por tienda en el handler es comportamiento intencional, no una fuga.
