# Plan → Module Matrix (Store Plans)

**Status:** active — single source of truth for what modules a store may hold per plan.
**Last reviewed:** 2026-09-30.

This document defines which `Module` rows each `StorePlan` grants. It is the spec that
`PlanModuleConvergence` (EF migration `20260930090000_PlanModuleConvergence`) applies to
`StorePlanModule`, and that per-store reconciliation then applies to `StoreModule`.

## 2. Own modules per plan

Each plan is defined by the modules it adds **on top of the previous plan**. The `StorePlanModule`
table stores the **cumulative** result, not this own-set.

| Plan | Id | Own modules (excludes the previous plan) | Count |
|---|---|---|---|
| **Gratis** | 1 | Ventas (2), Inventario (3), Sincronización (4), Reportes (5), Gestión (7) | 5 |
| **Pago** | 2 | Estadísticas (6), Gastos (8), Facturación (9), Historiales (10), Créditos (11) | 5 |
| **Superior** | 3 | Ventas Mayoristas (12), Almacenes (13), Múltiples tiendas (14), Múltiples monedas (15), Elaboración (17), Catálogo web (18) | 6 |
| **VIP** | 4 | Múltiples pagos (16) | 1 |

Equivalently: a plan `P` includes module `m` when `m`'s own plan id is `<= P`. That single
rule is how the migration encodes the matrix.

### Cumulative totals

| Plan | Own | Cumulative | Modules |
|---|---|---|---|
| Gratis | 5 | **5** | 2, 3, 4, 5, 7 |
| Pago | 5 | **10** | 2, 3, 4, 5, 7, 6, 8, 9, 10, 11 |
| Superior | 6 | **16** | previous + 12, 13, 14, 15, 17, 18 |
| VIP | 1 | **17** | previous + 16 — every store-available module |

Administración (1) appears in **no** plan, at any level.

## 3. How the code resolves a store's module universe

`ChangeStorePlanCommand.ApplyPlanModules`
(`backend/src/Application/Features/StoreManagement/Stores/Commands/ChangeStorePlan/ChangeStorePlanCommand.cs:165`):

```csharp
var catalog = await _moduleRepository.GetAvailableModulesToStore();   // IsActive && AvailableToStore && has >=1 active store feature
var freeModuleIds = catalog.Where(m => m.PriceIncluded).Select(m => m.Id);
var planModuleIds  = targetPlan.StorePlanModules.Select(spm => spm.ModuleId);
var universe = freeModuleIds.Union(planModuleIds).Distinct();
```

Then it soft-deletes active modules outside the universe, inserts the missing ones,
reactivates soft-deleted ones, and regenerates `StoreRoleFeature`.

Three known gaps make a real store drift from its plan:

1. **`ChangeStorePlanCommand.cs:116-117`** — when the store is already on the target plan the
   handler returns success **before** reconciling. Adding a module to a plan never reaches
   the stores already on it.
2. **`ToggleStorePlanCommand.cs:155`** — adds a single paid module, no universe reconciliation.
3. **`UpdateStoreCommand.cs:192`**, **`UpdateStoreModulePricingCommand.cs:155`** — write
   `StoreModule` rows without reconciling against the plan.

`CreateStoreCommandValidator.cs:53` also caps every store-creation request at the active
**Pago** plan's catalog, so no store is ever born Superior or VIP — it is created on Pago and
then upgraded.

## 4. StoreRoleFeature is part of "having" a module

A `StoreModule` row alone grants nothing. `AllowedFeaturesService` resolves `FeatureIds` only
through `StoreRoleFeature`, which is generated by `StoreRoleFeatureGenerator` from the
`StoreRoleFeatures` C# enum (`[HasModule]` + `[HasFeature]` + `[HasRoles]`). Per
`AGENTS.md`, an enum entry missing `[HasModule]`/`[HasFeature]` is **silently dropped**.

So "assign the corresponding modules to each store" means both tables:

- `StoreModule` — the plan's modules, active
- `StoreRoleFeature` — one row per (feature, role) for the features of those modules

The feature→role pairs are fixed:

## 5. Invariants

1. `StorePlanModule` must equal the cumulative matrix in §2 for every plan.
2. No row in `StorePlanModule` may reference a module with `AvailableToStore = false`.
3. A store's **active** `StoreModule` set must equal its plan's cumulative set.
4. A store's active `StoreRoleFeature` set must equal the features of its active modules,
   with the role sets in §4.
5. Extras are **soft-deleted**, never hard-deleted, and prices on reactivated rows are
   preserved — negotiated per-store pricing is not overwritten by a reconciliation.
