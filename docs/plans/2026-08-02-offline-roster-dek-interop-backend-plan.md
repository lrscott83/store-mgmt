# Offline Roster — DEK Interop Proof Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Date: 2026-08-02
Scope: `backend/` owns Tasks 1-3. Task 4 records the frontend follow-up; do not implement it here — it belongs to the `at-rest-encryption-frontend` change (branch `feat/at-rest-encryption-frontend`, currently verify-BLOCKED on exactly this gap).

**Goal:** Prove that a wrapped DEK produced by the backend can actually be recovered by a consumer that is not the backend. Today nothing on either side proves this, and the failure mode is unreadable data rather than an error.

**Architecture:** Three changes at three different distances from the wire, and they are not substitutes for one another — (1) an E2E test that unwraps a genuinely exported bundle, proving the whole chain including which value feeds the KEK; (2) a committed cross-implementation vector that both stacks read, so a parameter change on either side breaks a test instead of a tablet; (3) putting the iteration count on the wire, which removes the one drift class the other two can only detect after the fact.

**Tech Stack:** .NET 8, MediatR 12, EF Core, xUnit + Moq + FluentAssertions (unit), Mvc.Testing (E2E). Solution: `backend/src/SMCA.sln`.

## The defect, stated precisely

`ExportOfflineRosterTests.cs:58-60` is the only place an exported `wrappedDek` is ever asserted on:

```csharp
user.WrappedDek.Should().NotBeNullOrEmpty();
user.WrapSalt.Should().NotBeNullOrEmpty();
user.WrapIv.Should().NotBeNullOrEmpty();
```

It never unwraps it. A `WrapDek` that returned 48 bytes of noise would pass every assertion in that file.

`StoreKeyWrapServiceTests.cs:16-51` does round-trip the wrap, but with `RandomNumberGenerator.GetBytes` on both ends and .NET on both sides. It proves `AesGcm` is self-consistent. It cannot detect a parameter that both the producer and the consumer read the same wrong way, because there is only one reader.

A repo-wide search for a committed `wrappedDek` / `wrapSalt` / `wrapIv` value returns nothing. There is no fixed vector anywhere in `backend/`.

Consequences, in order of severity:

1. **No test anywhere proves the DEK is recoverable.** The PWA's `unwrapDek` is already live in production on both login paths (`frontend-react/apps/web-store-pos/app/shared/lib/stores/auth-store.ts`, `.../offline/offline-auth-service.ts`). It was written by transcribing `StoreKeyWrapService.cs` into TypeScript, and its known-answer fixture was generated by transcribing the same C# a second time into Node. Same reading, twice. A misreading survives both.
2. **The KEK input is an assumption, not a verified fact.** `WrapDek(su.User.Password, dek)` feeds the *stored hash*, not the raw password (`ExportOfflineRosterQuery.cs:102`). Nothing tests that a client deriving the KEK from the stored hash — rather than from the password — is the one that succeeds.
3. **`KekIterations` does not travel.** `StoreKeyWrapService.cs:9` hardcodes `210_000` and the value never reaches the client, unlike `verifier.iterations`, which is carried on `OfflineVerifierDto` and read by the device. Both sides hold private copies of the same constant. Changing it on the backend produces bundles that no deployed device can open, and no test on either side fails.

Task 1 fixes (1) and (2). Task 2 fixes the "same reading twice" half of (1) permanently. Task 3 fixes (3), and is the only one that prevents the drift rather than detecting it afterwards.

## Global Constraints

- **The wrap algorithm does not change.** HKDF-SHA256 for the DEK, PBKDF2-HMAC-SHA256 / 210 000 / SHA-256 / 32 bytes for the KEK over the stored hash, AES-GCM with a 16-byte tag and 12-byte IV, `ciphertext‖tag`, all Base64. This plan proves the existing contract; it does not renegotiate it. Any task that finds itself changing `StoreKeyWrapService`'s math has gone wrong.
- **Do not weaken the service's surface to make it testable.** `WrapDek` generating its own random salt and IV is correct — reuse across wraps is the failure this design avoids. Task 2 obtains a fixed vector by *capturing* one output, not by making randomness injectable in production code.
- **The E2E suite already has everything Task 1 needs.** `DbTestHelpers.HashPassword(password)` is `Convert.ToBase64String(SHA256.HashData(...))` (`DbTestHelpers.cs:21-22`), seeded users use `"Password123"`, and `IStoreDataKeyProvider` is resolvable from the DI scope (`Program.cs:64-65`). Do not introduce a new fixture, a new secret, or a second seeding path.
- **`ResponseResult<T>`** remains the handler return shape. JSON casing stays default camelCase; do not add JSON config.
- **Task 3 is a breaking contract change for the PWA.** It is safe only in the order given in Task 4.

### Task 1: Prove the exported bundle is unwrappable, end to end

The highest-value task in this plan and the cheapest. It is the test that would have caught a wrong KEK input, a wrong iteration count, or a wrong byte layout — any of them — on the day the backend shipped.

**Files:**
- Modify: `SMCA.WebApi.E2ETests/Users/ExportOfflineRosterTests.cs`

**Steps:**
- [ ] Add a test `SuperAdmin_export_roster_dek_is_recoverable_from_wire_fields_only`.
- [ ] Seed as `SuperAdmin_export_roster_returns_full_bundle` already does, with a store user whose password is the literal `"Password123"`.
- [ ] Export via `GET /api/v1/StoreUsers/{storeId}/offline-roster` and take the first user.
- [ ] Reconstruct the KEK **using only values available to a client**: `storedHash = Convert.ToBase64String(SHA256.HashData(Encoding.UTF8.GetBytes("Password123")))`, then `Rfc2898DeriveBytes.Pbkdf2(Encoding.UTF8.GetBytes(storedHash), Convert.FromBase64String(user.WrapSalt), 210_000, HashAlgorithmName.SHA256, 32)`. Do NOT call `StoreKeyWrapService` or any internal to obtain the KEK — the point is that the wire fields suffice.
- [ ] Split `Convert.FromBase64String(user.WrappedDek)` into `ciphertext = wrapped[..^16]` and `tag = wrapped[^16..]`, then `new AesGcm(kek, 16).Decrypt(iv, ciphertext, tag, recovered)`.
- [ ] Resolve `IStoreDataKeyProvider` from a DI scope and assert `recovered` equals `provider.GetDek(owner.StoreId)` byte for byte.
- [ ] Add a negative case: the same reconstruction using the **raw** password instead of the stored hash MUST fail to decrypt (`AesGcm.Decrypt` throws `AuthenticationTagMismatchException`). Without this, the test passes for a client that guessed the input wrong in a compensating way.
- [ ] Run `dotnet test` on the E2E project. Both cases green.

**Definition of done:** the assertion compares recovered bytes against `GetDek`, not against a non-null check, and the negative case pins which input feeds the KEK.

### Task 2: Commit a cross-implementation vector both stacks read

Task 1 proves .NET can unwrap .NET through the wire shape. It still does not prove TypeScript can. This task produces one fixed vector, checked in, that both test suites must agree on.

**Files:**
- Add: `docs/contracts/offline-roster-dek-kat.json`
- Add: `Application.Tests/Services/Authentication/StoreKeyWrapInteropTests.cs`

**Steps:**
- [ ] Write a one-shot generator (a `[Fact]` you run once and then delete, or a scratch console project outside the solution) that calls the real `StoreKeyWrapService.WrapDek` with a **fixed** stored hash and a **fixed** 32-byte DEK, and prints the resulting `WrappedDek` / `WrapSalt` / `WrapIv`. Do not add randomness injection to production code to achieve this — capture one real output.
- [ ] Commit the captured values to `docs/contracts/offline-roster-dek-kat.json`. Required fields: `password` (the plaintext the hash derives from), `storedPasswordHash`, `expectedDek` (Base64), `wrappedDek`, `wrapSalt`, `wrapIv`, `iterations`, and a `_header` block carrying `provenance: "dotnet-backend"`, the backend commit SHA it was generated at, and the .NET version.
- [ ] Add `StoreKeyWrapInteropTests` with a test that reads the JSON, derives the KEK from `storedPasswordHash` + `wrapSalt` + `iterations` using only documented parameters, unwraps `wrappedDek`, and asserts it equals `expectedDek`. It must NOT call `WrapDek` — a test that re-wraps and compares would go green even if the committed vector were stale.
- [ ] Add a second test asserting `HKDF.DeriveKey` over the vector's documented master secret and store id reproduces `expectedDek`, so the DEK derivation is pinned too, not only the wrapping.
- [ ] Run `dotnet test`. Green.
- [ ] Deliberately change `KekIterations` to `210_001` locally and confirm the interop test FAILS. Restore it. Record the observation in the PR description — an unverified guard is not a guard.

**Definition of done:** the vector file exists with honest provenance metadata, the interop test reads it rather than regenerating it, and the iteration-drift check was observed failing.

### Task 3: Put the iteration count on the wire

`verifier.iterations` already travels (`OfflineVerifierDto`, asserted at `ExportOfflineRosterTests.cs:56`). The wrap's iteration count does not. That asymmetry has no justification and it is the only silent-drift channel left after Tasks 1 and 2.

**Files:**
- Modify: `Application/Abstractions/Authentication/IStoreKeyWrapService.cs`, `Application/Services/Authentication/StoreKeyWrapService.cs`
- Modify: `Application/Dtos/Management/StoreUsers/OfflineRosterUserDto.cs`
- Modify: `Application/Features/Management/Users/Queries/ExportOfflineRoster/ExportOfflineRosterQuery.cs`
- Modify: `Application.Tests/.../ExportOfflineRosterQueryHandlerTests.cs`, `SMCA.WebApi.E2ETests/Users/ExportOfflineRosterTests.cs`

**Steps:**
- [ ] Add `int Iterations` to `WrappedDekResult` and populate it from `KekIterations` — the service reports what it actually used, it does not read a second copy of the constant.
- [ ] Add `public int WrapIterations { get; set; }` to `OfflineRosterUserDto`. Serializes as `wrapIterations`.
- [ ] Populate it in the export handler from the `WrapDek` result.
- [ ] Unit test: the handler emits `wrapIterations == 210_000`.
- [ ] E2E: extend Task 1's test to derive the KEK from `user.WrapIterations` rather than a literal `210_000`, so the test consumes the wire value the way a client will.
- [ ] `FormatVersion` stays at `2`. Adding a field to a v2 bundle is backward compatible: existing clients that hardcode the count keep working, and clients that read it get the safe behaviour. Do NOT bump to 3.
- [ ] Run `dotnet test` on both projects. Green.

**Definition of done:** a client can derive the KEK entirely from the bundle, with no compiled-in constant.
