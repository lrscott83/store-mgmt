### 3. Billing/pricing for paid modules

- **Price model**: `Module.Price` (catalog) + `PercentDiscountPrice` + `DiscountPrice`. Effective price = `CurrentPriceServiceUtils.GetCurrentPrice(price, percent, discount)` = `price − price×percent/100 − discount`, clamped ≥ 0 (`Domain/Common/Utils/CurrentPriceServiceUtils.cs:11-17`). **Price 2 + 100% percent discount → effective 0** (matches the user's intent: paid-looking catalog, free in practice).
- **Where price/discount live in DB**: catalog `Module` table; per-store snapshot in `StoreModule` (`Price`, `ModulePrice`, `ModuleDiscountPrice`, `ModulePercentDiscountPrice`, `ModulePriceIncluded`).
- **Current precedent**: migration `20260901163808_UpdateModulePricesV3` + script `backend/scripts/10-update-module-prices-v3.sql` set all paid modules to `Price=2, PercentDiscountPrice=50` → effective 1 USD. The Warehouses module wants `Price=2, PercentDiscountPrice=100` → effective 0.
- **Plan types**: `BillingService.GetStoreBillingSummaryAsync` (`Application/Services/Billing/BillingService.cs:46-115`) — `PlanType = "Paid"` iff store has any non-`PriceIncluded` StoreModule AND `PaymentStartDate != null`. **⚠️ Assigning a paid module to an existing Free store (PaymentStartDate=null) does NOT flip its plan (PaymentStartDate stays null → still "Free"/NoAplica)**; but a Paid store (PaymentStartDate set) with Vencido status loses the module via `FilterForBilling`.
- **Purchase/activation paths**: `UpdateStoreCommand` (module add), `ToggleStorePlanCommand` (Free→Paid activates all paid modules), `RegisterStorePaymentCommand` (`Application/Features/StoreManagement/StorePayments/Commands/RegisterStorePayment/RegisterStorePaymentCommand.cs:74` — amount = sum of `GetCurrentPrice` over active non-free StoreModules).
- **⚠️ Billing side effects of per-store assignment**: `GetStoresToCollectQuery.cs:88-95` — PorVencer/EnGracia stores get `Amount` summed over ALL active paid StoreModules. A 100%-discounted Warehouses module contributes `GetCurrentPrice(2, 100, 0) = 0` — no amount impact. But it ADDS the module to the list of modules to deactivate when a Paid store toggles to Free (`ToggleStorePlanCommand.ApplyPaidToFree:176-193`).

## Approaches

1. **Seed catalog via HasData + migration INSERTs per-store rows with raw SQL** (recommended)
   - Add `ModuleType.Warehouses = 12`, two `FeatureType` values (36 + new id), enum attributes, both `HasData` configs; generate EF migration (produces `InsertData` for Module/Feature); hand-extend the migration with `migrationBuilder.Sql` INSERT-SELECTs into `StoreModule`/`StoreRoleFeature` for every existing store (pattern: `UpdateModulePricesV3` Sql usage + script 03 inserts). Replicate everything in `backend/scripts/11-*.sql`.
   - Pros: single source of truth (HasData) — future databases get the catalog automatically; migration is the only place that touches existing stores; VPS script mirrors it exactly; E2E fixture auto-applies it.
   - Cons: composite-key INSERT-SELECT for StoreRoleFeature must set audit columns (`CreatedDate`, `CreatedBy`, `IsActive`) and `TenantId` (available from `Store`); `CreatedBy` for a SuperAdmin has no obvious value — may need a fixed GUID (`DataUtils.SuperAdminUser.Id`); ON CONFLICT DO NOTHING needed for idempotency.
   - Effort: Medium.

2. **Migration with raw SQL only (no HasData change)**
   - Keep configs untouched; write the entire migration as `migrationBuilder.Sql` INSERTs for Module/Feature/StoreModule/StoreRoleFeature.
   - Pros: no snapshot churn; catalog rows still versioned by the migration.
   - Cons: **violates the repo's HasData seeding convention** — a fresh database rebuilt from migrations would still get the rows (migrations replay), but the model snapshot and configs diverge; `ResetDataAsync` preserves seed rows by table, not by origin, so no direct breakage, but future EF `HasData` diffs would try to delete these rows (snapshot mismatch → next generated migration emits DeleteData for them). RISKY.
   - Effort: Medium.

3. **Runtime backfill command (like `ActivateFeaturesCommand`) + VPS SQL script only**
   - Extend/reuse a runtime command to create the module/features and assign to stores; VPS runs a plain SQL script (no EF migration).
   - Pros: no migration complexity; activate precedent exists for feature 36.
   - Cons: **user explicitly required an EF migration that also assigns to existing stores**; violates the migration-then-script order rule; E2E would depend on calling the command.
   - Effort: Low-Medium but non-compliant with the stated requirement.

## Recommendation

**Approach 1.** It follows the repo's established conventions exactly (HasData → generated migration → hand-extended `Sql` for data ops → mirrored numbered script), keeps the model snapshot authoritative, and the E2E fixture proves the migration applies cleanly on every run. The per-store INSERT-SELECT is new territory but each ingredient has precedent: `UpdateModulePricesV3` (Sql in migration touching StoreModule), script 03 (catalog INSERTs + setval + history registration), `AuthzSeed`/`CreateStoreService` (exact StoreModule/StoreRoleFeature column values to mimic).

## Risks

- **Module id 12 collision with the Elaboration plan** — `docs/plans/2026-09-04-elaboration-module.md:137` reserves `ModuleType.Elaboration = 12`. If Warehouses takes 12, the Elaboration plan must renumber (or vice versa). Proposal must pin the decision.
- **FeatureType 36 seeding semantics flip** — moving feature 36 from "runtime-created by activate" to "migration-seeded" changes `FeatureSeed.RestoreAsync` assumptions (`FeatureSeed.cs:107-111` deletes it when `!snap.WarehousesExisted`). After the migration, 36 ALWAYS exists → `snap.WarehousesExisted` becomes always-true → restore deletes nothing (safe), but the existing E2E tests' semantics shift silently. Existing tests are untouchable — this needs verification that they still pass (they should: restore only deletes when it was absent before).
- **`ActivateFeaturesCommand` double-create guard** — with 36 seeded, activate's `if (warehousesFeature == null)` branch just skips; no insert; `SaveChangesAsync > 0` may now return... (still true: repository `UpdateAsync` marks Modified → returns > 0 rows, per test note in `FeaturesActivateTests.cs:46-47`). Safe, but should be verified in E2E.
- **Billing side effects** — assigning a paid module to existing stores: (a) Free stores keep `PaymentStartDate=null` → PlanType stays "Free", billing status NoAplica, module still accessible (NoAplica passes the filter); (b) Paid Vencido stores lose the new module (FilterForBilling drops non-included) — intended behavior matching other paid modules; (c) `ToggleStorePlan` Paid→Free will deactivate the new module's StoreModule + StoreRoleFeatures; (d) `GetStoresToCollect` amount unchanged (100% discount → 0).
- **`Register` now auto-assigns the new module** — `RegisterCommand` assigns ALL available modules to new stores, so the Warehouses module (AvailableToStore=true) lands on every newly-registered store automatically. That is consistent with how Reports/Statistics etc. behave today. `AuthRegisterDataAssertionsTests.Register_assigns_all_available_modules_including_paid` (line 178-219) derives expectations dynamically — should keep passing.
- **NoTracking trap** — any runtime code touching loaded entities must attach before save (CLAUDE.md gotcha; `ToggleStorePlanCommand.cs:106-108` documents the pattern). Migration SQL is unaffected.
- **Sequence fix-ups** — script 03 shows `"Feature"`/`"Module"` sequences must be `setval`-bumped after explicit PK inserts (explicit ids don't advance serials). For StoreModule/StoreRoleFeature (composite PKs, no serial) this is a non-issue, but the catalog inserts in the VPS script need it.
- **StoreRoleFeature INSERT-SELECT audit columns** — per-store assignment needs `TenantId` (from `Store.TenantId`), `CreatedDate` (now), `CreatedBy` (a fixed system GUID — `DataUtils.SuperAdminUser.Id` is the only canonical choice), `IsActive=true`. Must match `StoreRoleFeature.Create` output shape exactly.
- **E2E fixture data wipe** — `ResetDataAsync` clears StoreModule/StoreRoleFeature every run, so the "existing stores get the module" behavior is only observable in a test that seeds a store and re-runs... actually NO: the fixture applies migrations ONCE per run BEFORE the reset; within a single run, stores created by earlier tests WILL get the module only via runtime paths, NOT via the migration (migration ran before they existed). **E2E tests for "existing store assignment" must assert the migration's effect via the fixture-applied state or via direct SQL verification against a pre-seeded store created before `MigrateAsync`... impossible.** Practical answer: E2E asserts (a) catalog rows exist post-migration (36 + new feature + module 12 with price 2/100%), (b) `Register`/`UpdateStore`/`ToggleStorePlan` runtime paths assign the module correctly, (c) the migration's per-store INSERT-SELECT is proven by the VPS script review + (optionally) a dedicated test that seeds a store, then manually invokes the same SQL block. **This is a key open question for the proposal.**
