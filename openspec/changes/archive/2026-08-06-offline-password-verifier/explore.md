## Exploration: offline-password-verifier

### Current State

**Bug #1 — offline login verifier derived from wrong input.**
- `backend/src/Application/Services/Authentication/OfflineVerifierService.cs:13-27` `CreateVerifier(string storedPasswordHash)` computes `PBKDF2(UTF8(storedPasswordHash), salt, 210_000, SHA256, 32)`.
- Interface: `backend/src/Application/Abstractions/Authentication/IOfflineVerifierService.cs:5-8`, `OfflineVerifierResult(Hash, Salt, Iterations)`.
- Sole caller: `backend/src/Application/Features/Management/Users/Queries/ExportOfflineRoster/ExportOfflineRosterQuery.cs:115` — `_offlineVerifierService.CreateVerifier(su.User.Password)`, i.e. the stored Argon2id PHC string.
- Frontend: `frontend-react/apps/web-store-pos/app/shared/lib/offline/offline-crypto.ts:81-88` `verifyOfflinePassword` computes `preHash = sha256Base64(password)` then `pbkdf2Base64(preHash, verifier.salt, verifier.iterations)` — derived from the **typed password**, never from the stored hash.
- These only agree when `storedPasswordHash === Base64(SHA256(password))` — the legacy raw-SHA256 format, never true for Argon2id.
- **The spec itself documents the stale assumption**: `openspec/specs/offline-auth/spec.md:78` "Password input | UTF-8 bytes of `User.Password` (stored Base64 SHA256 hash)" — written before the Argon2id migration (git log: `docs(sdd): archive the argon2id-password-hashing change` 4126b35, after the offline-auth spec was archived on 2026-08-04). The spec needs updating as part of this fix.

**Bug #2 (confirmed, HIGH PRIORITY, identical defect) — DEK wrap uses the same wrong input.**
- `backend/src/Application/Services/Authentication/StoreKeyWrapService.cs:15-42` `WrapDek(string storedPasswordHash, byte[] dek)` derives KEK = `PBKDF2(UTF8(storedPasswordHash), wrapSalt, 210_000, SHA256, 32)`, then AES-256-GCM-encrypts the DEK.
- Called at `ExportOfflineRosterQuery.cs:116` with `su.User.Password` (the same Argon2id PHC string).
- Frontend `frontend-react/apps/web-store-pos/app/shared/lib/offline/dek-unwrap.ts:46-62` `unwrapDek` computes `preHash = sha256Base64(password)` then `pbkdf2Base64(preHash, entry.wrapSalt, DEK_WRAP_ITERATIONS)` — same pre-hash-of-typed-password convention as the verifier, NOT the stored hash. The file's own header comment (`dek-unwrap.ts:1-12`) asserts this "matches `Encoding.UTF8.GetBytes(su.User.Password)` on the backend exactly" — true only under the legacy format, now stale.
- Confirmed by the **existing** E2E test `SuperAdmin_export_rawPassword_throwsAuthenticationTagMismatch` (`backend/src/SMCA.WebApi.E2ETests/Users/ExportOfflineRosterTests.cs:558-587`), which pins that deriving the KEK from the raw plaintext password fails — the DEK wrap has never been derivable from the plaintext password in the current code, meaning offline data unlock is as broken as offline login for any user whose hash isn't legacy SHA256.

**How the E2E suite hides both bugs**: `ExportOfflineRosterTests.cs:252-263` and `:530-541` read `storedPasswordHash` straight from the DB (`db.Set<User>()...Select(u => u.Password)`) and feed that same string into a local `UnwrapDek` helper (`:589-608`) that mirrors `StoreKeyWrapService` line for line. `DbTestHelpers.HashPassword` (`backend/src/SMCA.WebApi.E2ETests/Infrastructure/DbTestHelpers.cs:26,43-44`) uses the real `Argon2idHashPasswordService`, so these are genuine post-migration Argon2id hashes — the tests pass because they validate the backend against itself, never against the frontend's SHA256-of-typed-password convention. Same self-referential pattern as `OfflineVerifierServiceTests.cs` and `ExportOfflineRosterQueryHandlerTests.cs` (mocked `CreateVerifier`/`WrapDek`, opaque strings, never assert the semantics of the input).

**KAT vector status**: `docs/contracts/offline-roster-dek-kat.json` (provenance `dotnet-backend`, consumed by `backend/src/Application.Tests/Services/Authentication/StoreKeyWrapInteropTests.cs`) has `storedPasswordHash: "AIxwOS46v70PpHu8LtlqqZvUnhWXJ/y6Dy5qvrOp1gE="` — a 32-byte Base64 string, i.e. the legacy `Base64(SHA256(password))` shape, NOT an Argon2id PHC string. This vector predates the Argon2id migration and is now testing a scenario that no longer occurs. The frontend's own KAT fixture (`frontend-react/.../offline/__tests__/__fixtures__/dek-kat.json`) is explicitly self-labelled `"provenance": "node-transcription"`, a `"PLACEHOLDER — does NOT prove backend interop"`, deferred as WU3.3 and never landed — so **no cross-stack vector has ever existed** for this crypto path; both sides have only ever proven internal consistency with themselves.

### ExportOfflineRosterQuery shape

`backend/src/Application/Features/Management/Users/Queries/ExportOfflineRoster/ExportOfflineRosterQuery.cs` — `FormatVersion = 3` (line 40). Per user it builds `OfflineRosterUserDto` (`backend/src/Application/Dtos/Management/StoreUsers/OfflineRosterUserDto.cs`): Id, Login, FullName, IsActive, Roles, FeatureIds, StoreModuleIds, IsSuperAdmin, IsOwnerAdmin, IsReSeller, SelectedStoreId, `Verifier` (non-nullable `OfflineVerifierDto`, defaults `= new()` with empty strings/0), WrappedDek/WrapSalt/WrapIv/WrapIterations, PaymentDueDate/IsInTrial/PaymentStatus. `OfflineRosterDto` wraps BundleId/IssuedAt/ExpiresAt/FormatVersion/StoreId/Users. Frontend mirror: `roster-types.ts` `OfflineRosterUserDto`/`OfflineVerifier`/`OfflineRosterBundle` — structurally identical field-for-field, `verifier: OfflineVerifier` is currently REQUIRED (not optional/nullable).

**Gap found in the proposed fix's "frontend needs zero changes" claim**: `offline-auth-service.ts:105-112` throws `OfflineVerifierError` only when `!user.verifier || typeof user.verifier.hash !== 'string' || ...` — i.e. only when the field is missing/null/wrong-typed. Because `OfflineVerifierDto` is currently non-nullable (`Verifier { get; set; } = new();`), a backend that has no persisted verifier for a user (never logged in since the migration) would still serialize `Verifier: { hash: "", salt: "", iterations: 0 }` — all present, correctly typed — so the frontend's `typeof` guard does NOT catch it. It falls through to `verifyOfflinePassword`, which fails (derived PBKDF2 output never equals `""`), producing `OfflineInvalidPasswordError` — "wrong password" — instead of the intended graceful `OfflineVerifierError` ("no offline access yet"). **To get the graceful-degradation path this proposal expects, `OfflineVerifierDto.Verifier` must become nullable (`OfflineVerifierDto?`) so the backend can send an explicit `null`, and `roster-types.ts`'s `OfflineRosterUser.verifier` must become `OfflineVerifier | null` to match.** This is a real, small frontend change — not zero.

### Frontend impact assessment

- `offline-auth-service.ts`, `offline-crypto.ts`, `roster-store.ts`, `roster-http-service.ts` (`frontend-react/apps/web-store-pos/app/shared/lib/http/roster-http-service.ts`), `roster-serializer.ts` all consume the roster/verifier/wrap fields as opaque wire data — none compute anything from `User.Password`; they only ever derive from the typed password. **They require no algorithmic changes.**
- BUT (see gap above) `roster-types.ts`'s `OfflineVerifier`/nullability contract needs a small adjustment (`verifier: OfflineVerifier | null`) plus a corresponding `offline-auth-service.ts` guard already exists and would correctly handle `null` once the backend can send it — the `!user.verifier` check at line 106 already does the right thing for an actual `null`, it just never receives one today.
- `dek-unwrap.ts`'s header comment (lines 1-12) is now factually wrong ("matches `Encoding.UTF8.GetBytes(su.User.Password)`") and should be corrected regardless of the fix chosen, to avoid re-misleading a future reader.

### Recommendation evaluation

The proposed fix — **derive the verifier where the plaintext exists (register / login success / password change), persist it on `User`, have `ExportOfflineRosterQuery` read the persisted verifier instead of computing one from the stored hash, frontend unchanged** — is directionally correct and matches the plaintext-availability audit above (all four password-set/verify choke points are single, well-defined call sites: `CreateOwnerService.CreateOwnerAsync`, `AuthenticationService.IsValidUserAsync`/`LoginCommandHandler`, `CreateStoreUserCommandHandler`, `CreateReSellerCommandHandler`, `UpdateUserPasswordCommandHandler`).

Problems the code reveals with it, as stated:

1. **It only fixes bug #1 (login verifier), not bug #2 (DEK wrap) unless explicitly scoped to include it.** `StoreKeyWrapService.WrapDek` has the identical defect and is called from the exact same handler method (`ExportOfflineRosterQuery.cs:116`) one line below the verifier call. Any proposal/design that stops at "verifier" without also addressing `WrapDek`'s key material leaves offline data-at-rest unlock (DEK wrap) broken for every Argon2id user even after login verification is fixed. This should be treated as one fix, not two — recommend explicitly widening scope to "persist a password-derived pre-hash (or equivalent secret) at the same four choke points, and use it for BOTH the verifier and the KEK derivation."
2. **"Frontend unchanged" is not quite true.** `OfflineVerifierDto.Verifier` (and `roster-types.ts`'s `OfflineVerifier`) must become nullable for the graceful-degradation path (`OfflineVerifierError`) to actually trigger for users who have no persisted verifier — today the DTO's non-nullable default (`= new()`, empty strings) would silently misroute those users into "wrong password" instead. This is a small, mechanical frontend type change plus one new test, not a crypto change, but it is a change.
3. **Users who never re-authenticate since deployment.** Any store user whose last login/password-set predates this fix has no persisted verifier/pre-hash. They cannot get one until they next log in online (the whole point of the design), so their offline-provisioning experience is "no offline access until first online login post-migration" — this needs to be an explicit, communicated behavior, not a silent gap. This is compounded by the *existing* Argon2id migration: any user who hasn't logged in since Argon2id shipped already can't offline-login today (bug #1) and also cannot offline-unwrap-DEK today (bug #2) — so this "first login required" constraint is not new incremental risk introduced by the fix, it is the fix *resolving* an already-existing total breakage for that population, contingent on them logging in online at least once.
4. **Weaker parallel credential concern**: persisting `PBKDF2(pre-hash-of-password, salt, 210_000, SHA256, 32)` (or whatever exact primitive is chosen) alongside the Argon2id hash does NOT create a materially weaker *authentication* bypass, because both the verifier and the wrap already are, and always have been, world-readable-by-design once exported in the roster bundle (that is the whole point of an offline-capable verifier — it must be independently checkable without hitting the server, so it can never be as strong as a server-side, rate-limited, pepper-protected Argon2id check). The verifier's job is offline-device gatekeeping, not primary defense. However, worth flagging for the design phase: **do not derive the persisted pre-hash directly from Argon2's own output** (i.e. don't reuse `user.Password` verbatim for anything) — it should be derived independently from the plaintext at the point of capture (e.g. `SHA256(password)` matching the frontend's existing pre-hash convention exactly, so no NEW derivation logic has to be invented and pinned) and stored in a way that doesn't shortcut Argon2id's cost factor for an attacker who already has DB access (an attacker with DB read access already has the Argon2id hash and the offline verifier/wrap fields are only ever exported over authenticated API calls to admins, per `ExportOfflineRosterQuery.cs:76-84`'s `IsSuperAdminOrOwnerAdmin`/ownership checks — so the exposure surface for this new persisted column is "who already has DB read access", not "who can call the export API", and DB read access already exposes the Argon2id hash itself). Net: no meaningfully new attack surface, but this reasoning belongs explicitly in the design doc's security section, not asserted for free.

### Ready for Proposal

Yes. Scope should be widened, in the proposal, from "verifier" to "verifier + DEK wrap key material" (both derive from the same choke points and the same root cause); the DTO/type nullability change should be named as an explicit (small) frontend deliverable, not folded into "frontend unchanged"; and the three named E2E tests must be called out to the user for explicit authorization before any `StoreKeyWrapService` signature/semantics change lands.
