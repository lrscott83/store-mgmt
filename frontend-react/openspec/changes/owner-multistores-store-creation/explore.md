# Exploration — owner-multistores-store-creation

## Answers to design-critical questions (all file:line verified)

**Q1 — Resolving caller's OwnerId server-side:** `IHttpContextService` exposes `UserExternalId` (NameIdentifier claim), `IsSuperAdmin`, `IsOwnerAdmin`, `TenantId`, `StoreId` (HttpContextService.cs:45-48 — all from JWT claims). The handler resolves the caller's Owner via `IOwnerRepository.GetByUserIdIgnoreQueryFiltersAsync(userId)` (IOwnerRepository.cs:12). `httpContextService.StoreId` = the SELECTED store id claim — available without extra queries.

**Q2 — MultiStores active check (billing parity):** The exact same recipe as HasPermissionAttribute.cs:86-88 and GetMeQuery.cs:94-96: `IStoreModuleRepository.GetAvailableModulesByStoreIdAsync(selectedStoreId)` + `IBillingService.GetStoreBillingSummaryAsync(selectedStoreId)` + `StoreBillingUtils.FilterForBilling(modules, billing)` → module ids list → `Contains(14)`. Vencido billing filters paid modules (MultiStores is paid: ModuleEntityTypeConfiguration.cs:172-182 Price=5, PriceIncluded=false) → check fails → 403. This gives exact session parity with the frontend gate.

**Q3 — Inheriting selected store's modules:** `IStoreModuleRepository.GetStoreModulesByIdAsync(storeId)` (IStoreModuleRepository.cs:10) returns the store's StoreModule rows. Their ModuleIds feed `CreateStoreService.CreateStoreAsync(..., moduleIds)`. Validator requires non-empty + all available (GetAvailableModulesToStore — module 14 is AvailableToStore=true, IsActive=true → always passes validation since inherited ids came from an existing store; edge: selected store could hold a module later marked unavailable — acceptable, validator rejects with 400 ModuleIds).

**Q4 — OwnerId enforcement shape (CHOSEN):** Option (b) backend-forces: OwnerAdmin branch ignores body OwnerId and uses the caller's own owner (resolved via GetByUserIdIgnoreQueryFiltersAsync). Evidence: SetStoreActivationCommand.cs (owner-scoped command pattern, 2026-09-08 plan) uses httpContext claims, not body trust; validator's OwnerExists check runs before handler — for OwnerAdmin the frontend sends its own ownerId anyway, so validation stays green. Frontend reads its ownerId from... NOTE: user.storeModuleIds is in session but ownerId is NOT in CurrentUserDto — frontend will send `user.id`-derived owner? NO — frontend Store model has ownerId (models/store.ts:27) but currentUser does not. RESOLUTION: frontend sends the body as today (ownerId field required by validator); backend overrides it with the caller's own owner id and returns 403 if body ownerId ≠ caller owner id (fail-closed on mismatch, mirrors SetStoreActivation ownership stance). Simplest safe contract.

**Q5 — StoreRoleFeatures on creation:** CreateStoreService.cs:65-68 generates StoreRoleFeature rows for the new store from the module-derived feature ids (generator: Domain/Entities/Tenants/StoreRoleFeatureGenerator.cs). The creating owner's OwnerAdmin role gets role-features automatically → they can access/switch to the new store. No StoreUser row is created for the owner (owners access via Owner relation, SetMyStoreCommand.cs:47 uses GetActiveStoresByUserIdAsync = `s.Owner.UserId == userId` — new store is immediately switchable because OwnerId points at the caller's owner).

**Q6 — POST response & new store visibility:** my-stores page refetches via getMyStores() after save (same pattern as handlePlanSave in my-stores.tsx:118-150); new store appears as a card. No session refresh needed for the LIST, but `getUserByToken()` IS needed if we want selectedStoreId/menus to reflect anything — NOT needed here (we do NOT auto-switch the selected store; the card just appears; owner can switch via existing store-switcher with the new store now reachable through GetActiveStoresByUserIdAsync).

**Q7 — Modal template:** EditStoreModal (components/edit-store-modal.tsx) is the byte-level pattern: overlay div role=dialog aria-modal, w-full max-w-md card, name input with label + validation, error <p role=alert>, Button variant=fab with icons, data-testid conventions (`owner-store-name-input-*`). New CreateStoreModal: single name field, same structure, new data-testids (`my-stores-create-button`, `create-store-modal`, `create-store-name-input`, `create-store-submit`).

**Q8 — Playwright seeding (owner + MultiStores):** Persona owner-admin registers via REAL register flow → RegisterCommand creates store with ALL available modules (RegisterCommand.cs:70-83) → module 14 included → storeModuleIds will contain 14 (plan Pago/NoAplica → FilterForBilling passes all) → BUTTON VISIBLE by default in tests. To test the hidden state: degradeStoreToFreePlan(page, storeId) from support/store-fixture.ts:128 deletes StoreRoleFeature+StoreModule rows and re-inserts ONLY free modules (14 is paid → removed) → button hidden. That helper exists and is reusable (does NOT modify existing support files — we only import it).

**Q9 — Vitest pattern:** my-stores.test.tsx mocks auth-store (mockUser mutable), storeHttpService (getter-based vi.fn mocks), loaders, toast, confirmDialog. New tests extend: mock createStore in the service getter map, assert button visibility by storeModuleIds (user.storeModuleIds includes 14 vs not), modal open/validate/submit flow, service error display.

**Q10 — Page gate vs button gate:** Page /management/my-stores loader = featureLoader([EFeatures.Stores]) (my-stores.tsx:16) — feature 73 gate, role-agnostic (owner/superadmin/store-user-with-feature can render). Button gate = user.isOwnerAdmin && isModuleAvailable(user, EModules.MultiStores). SuperAdmin does NOT see the button (my-stores view is for owners; superadmin has /admin/stores with its own + button). No conflict.
